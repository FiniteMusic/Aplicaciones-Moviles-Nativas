# 2. El problema del aislamiento de los modelos de lenguaje

## 2.1. Introducción

Los modelos de lenguaje grandes (LLM) pueden explicar código, proponer modificaciones y generar instrucciones para manipular archivos. Sin embargo, **generar una instrucción no equivale a ejecutarla**. Para que una operación afecte realmente a una computadora se necesita un programa que reciba la solicitud y disponga de acceso autorizado al recurso correspondiente.

Esta distinción permite comprender por qué una integración como el Model Context Protocol (MCP) resulta útil en los entornos de desarrollo: conecta una aplicación que utiliza un modelo con herramientas capaces de actuar sobre recursos reales, sin atribuir al modelo acceso directo al sistema operativo.

## 2.2. ¿Por qué un LLM no puede ver ni modificar archivos por sí mismo?

En una interacción básica, un modelo recibe una entrada representada mediante tokens y produce una salida. Sus cálculos permiten generar una respuesta, pero **la inferencia del modelo, por sí sola, no abre archivos, ejecuta programas ni realiza llamadas al sistema operativo de la computadora del usuario**.

Por ejemplo, ante la solicitud «crea un archivo `notas.txt`», un modelo sin herramientas puede responder con el siguiente código:

```python
with open("notas.txt", "w", encoding="utf-8") as archivo:
    archivo.write("Prueba de escritura")
```

Ese texto describe una operación válida, pero el archivo no se crea hasta que un proceso con acceso al sistema de archivos ejecuta el código. Del mismo modo, un modelo puede sugerir cómo corregir un proyecto sin haber leído los archivos reales de ese proyecto.

Esta limitación se refiere al **modelo aislado**, no a todas las aplicaciones de inteligencia artificial: algunas aplicaciones sí proporcionan archivos como contexto y herramientas para leerlos o modificarlos.

## 2.3. Razones de arquitectura

El aislamiento tiene una explicación técnica. En muchas aplicaciones, el modelo se ejecuta en infraestructura remota y la persona interactúa con él desde un navegador o editor. El modelo no recibe automáticamente una conexión al disco local, ni conoce la estructura de carpetas de Windows 11.

Para realizar una operación local debe existir un canal explícito entre la aplicación y un componente que pueda interactuar con el sistema operativo. La arquitectura puede resumirse así:

```text
Persona usuaria
      |
      v
Aplicación (por ejemplo, VS Code)
      |
      v
Modelo de lenguaje
      |
      | Solicitud de uso de una herramienta
      v
Aplicación / cliente MCP
      |
      v
Servidor MCP de sistema de archivos
      |
      v
Directorio local autorizado
```

Este esquema es conceptual: el **host** administra la interacción con el modelo y el cliente MCP; el **servidor MCP** implementa las operaciones sobre archivos. El modelo no establece por sí mismo una conexión directa con el disco.

La documentación de arquitectura de MCP distingue precisamente las funciones del host, los clientes y los servidores (Model Context Protocol, 2026).

## 2.4. Razones de seguridad

Además de la arquitectura, el aislamiento responde a necesidades de protección. Dar acceso irrestricto a un asistente podría exponer documentos privados, código confidencial, contraseñas o archivos necesarios para el funcionamiento del equipo.

Los riesgos principales incluyen:

| Riesgo | Ejemplo | Consecuencia posible |
|---|---|---|
| Lectura no autorizada | Solicitar un archivo personal ajeno al proyecto | Exposición de información privada |
| Escritura no deseada | Sobrescribir un archivo de código | Pérdida de trabajo o fallas en el proyecto |
| Acceso excesivo | Autorizar toda la carpeta de usuario | Ampliación innecesaria de los archivos accesibles |
| Inyección de instrucciones | Un archivo contiene órdenes dirigidas al asistente | Desvío de la tarea solicitada |

La **inyección indirecta de instrucciones** ocurre cuando contenido externo —por ejemplo, un archivo que el asistente debe resumir— incluye texto diseñado para alterar su comportamiento. OWASP identifica este riesgo y recomienda limitar privilegios, distinguir datos de instrucciones y exigir aprobación humana para acciones de alto impacto (OWASP, 2025).

## 2.5. ¿Cómo contribuye MCP a resolver el aislamiento?

MCP es un protocolo abierto que estandariza la comunicación entre aplicaciones de inteligencia artificial y servidores que ofrecen capacidades externas. Un servidor puede publicar herramientas para leer archivos, buscar documentos o ejecutar otras operaciones específicas.

En nuestro proyecto, la integración se organizará de la siguiente manera:

| Componente | Función en la práctica |
|---|---|
| Visual Studio Code | Aplicación host donde se realiza la interacción |
| Funcionalidad de chat y cliente MCP de VS Code | Gestiona el uso de herramientas y la comunicación con el servidor |
| Modelo de lenguaje | Interpreta la solicitud y puede proponer una llamada a una herramienta disponible |
| `@modelcontextprotocol/server-filesystem` | Implementa operaciones sobre archivos y valida el alcance autorizado |
| Carpeta de pruebas | Contiene los archivos sobre los que permitiremos operar |

**MCP no elimina por sí solo los riesgos de seguridad.** La protección depende también de la configuración del host, el comportamiento del servidor, las autorizaciones y los permisos del sistema operativo. El servidor de referencia de sistema de archivos permite definir directorios autorizados y dispone de una herramienta para consultarlos; las operaciones deben permanecer dentro de ese alcance (Model Context Protocol, s. f.).

## 2.6. Ejemplo aplicado a Windows 11 y VS Code

Para la práctica se creará una carpeta específica, por ejemplo:

```text
C:\Users\Marc_\Documents\ESCOM\Aplicaciones Moviles Nativas\Aplicaciones-Moviles-Nativas\Tarea 1\Pruebas
```
Si el servidor queda autorizado únicamente para esa carpeta, podrá realizar las operaciones que exponga sobre sus archivos y subdirectorios. En cambio, una solicitud para leer un archivo fuera del directorio autorizado deberá ser rechazada por la validación de rutas del servidor, incluso si el modelo propone la operación.

La configuración del directorio permitido **no equivale a un modo de solo lectura**: el servidor de referencia también ofrece herramientas de escritura y edición. Para impedir modificaciones se necesitan controles adicionales, como permisos del sistema operativo, una configuración realmente limitada a lectura o aislamiento mediante contenedores.

Además, las confirmaciones que muestre VS Code dependen de la configuración del cliente y de las políticas de aprobación activas; no debe asumirse que toda llamada se confirma siempre de manera individual.

## 2.7. Conclusión

El aislamiento de un LLM tiene dos fundamentos complementarios. Desde la arquitectura, el modelo genera resultados pero no posee automáticamente un canal hacia el sistema de archivos local. Desde la seguridad, limitar ese acceso ayuda a reducir la exposición de información y las modificaciones no autorizadas.

MCP permite conectar una aplicación que utiliza un modelo con servidores que ofrecen capacidades concretas. En el caso del servidor de sistema de archivos, las operaciones reales las ejecuta el servidor dentro de los límites configurados, no el modelo directamente. Esta separación será la base de nuestra instalación, nuestras evidencias y la prueba de acceso fuera del directorio autorizado.
