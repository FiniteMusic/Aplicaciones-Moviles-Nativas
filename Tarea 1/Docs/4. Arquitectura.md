# 4. Arquitectura del Model Context Protocol (MCP)

## 4.1. Introducción

El **Model Context Protocol (MCP)** es un protocolo abierto que estandariza la comunicación entre aplicaciones que incorporan modelos de lenguaje y servicios que proporcionan herramientas, datos o instrucciones reutilizables. Su arquitectura separa la aplicación que organiza la interacción con el modelo de los componentes que ejecutan operaciones sobre sistemas externos.

Esta separación permite integrar distintas fuentes de información sin diseñar una conexión exclusiva para cada combinación de aplicación y servicio. MCP define roles, mensajes y mecanismos de transporte; no exige que el modelo de lenguaje ejecute directamente las operaciones ni que todos los servidores ofrezcan las mismas capacidades.


## 4.2. Modelo host / cliente / servidor

MCP distingue tres roles principales:

| Componente | Responsabilidad | Ejemplo general |
|---|---|---|
| **Host** | Aplicación que contiene la experiencia de usuario, coordina el uso del modelo y administra las conexiones y políticas de acceso. | Un editor con asistente de programación o una aplicación de chat con herramientas. |
| **Cliente MCP** | Componente del host que se comunica con un servidor MCP, consulta sus capacidades y solicita operaciones mediante el protocolo. | El conector MCP integrado en una aplicación de IA. |
| **Servidor MCP** | Programa o servicio que publica capacidades y atiende solicitudes de los clientes, normalmente accediendo a recursos o sistemas bajo permisos definidos. | Un servidor que ofrece búsqueda documental o lectura de archivos. |

Una misma aplicación host puede administrar **varios clientes MCP**, cada uno conectado a un servidor distinto. El cliente MCP no debe confundirse con la persona usuaria ni con el modelo de lenguaje: es el componente de software que implementa la comunicación con el servidor.

### Flujo conceptual de una operación

```text
Persona usuaria
      |
      v
Host (aplicación con modelo de IA)
      |
      v
Cliente MCP  <---- mensajes MCP ---->  Servidor MCP
                                           |
                                           v
                                  Recurso o sistema externo
```

Por ejemplo, si una persona solicita localizar un documento, el host puede presentar al modelo las herramientas disponibles. Cuando se selecciona una herramienta adecuada, el cliente MCP envía la solicitud al servidor; este realiza la operación permitida y devuelve el resultado. El host incorpora ese resultado a la interacción con el modelo. **El modelo no establece por sí mismo una conexión directa con el disco ni ejecuta automáticamente llamadas al sistema operativo**.

## 4.3. Primitivas del lado del servidor

Las principales capacidades que puede publicar un servidor MCP son **tools, resources y prompts**. Son categorías diferentes y no deben utilizarse como sinónimos.

### 4.3.1. Herramientas (*tools*)

Las herramientas representan operaciones invocables. Cada una puede incluir nombre, descripción y un esquema de parámetros que indica qué argumentos acepta. El cliente consulta el catálogo mediante `tools/list` e invoca una operación mediante `tools/call`.

Ejemplos generales: buscar un archivo, consultar una base de datos, crear un registro o ejecutar una validación. Algunas herramientas son de solo lectura; otras pueden producir efectos sobre el entorno. La descripción de una herramienta ayuda a determinar cuándo utilizarla, pero **no constituye por sí misma un mecanismo de autorización**.

### 4.3.2. Recursos (*resources*)

Los recursos permiten exponer información identificable mediante URI para que el cliente pueda descubrirla y leerla. Entre los métodos asociados se encuentran `resources/list` y `resources/read`. También pueden existir plantillas de URI para recursos parametrizados.

Ejemplos generales: documentación técnica, registros de una aplicación o el contenido de un archivo publicado por un servidor. A diferencia de una herramienta, el recurso representa principalmente **información accesible**, no una acción que deba ejecutarse.

### 4.3.3. Plantillas de prompt (*prompts*)

Los prompts son plantillas reutilizables que un servidor ofrece para estructurar una interacción. Pueden admitir argumentos, por ejemplo, el nombre de un lenguaje de programación o el tipo de documento que se desea analizar. El cliente puede consultar `prompts/list` y obtener una plantilla concreta con `prompts/get`.

Ejemplo: una plantilla para revisar código que incorpore instrucciones de análisis y campos configurables. Un prompt **no equivale a una herramienta**: proporciona contenido para orientar una tarea, pero no ejecuta por sí solo una modificación externa.

### Comparación de las tres primitivas

| Primitiva | Pregunta que responde | Función principal |
|---|---|---|
| Tools | ¿Qué operación se puede realizar? | Ejecutar una capacidad expuesta por el servidor. |
| Resources | ¿Qué información se puede consultar? | Proporcionar contenido identificado mediante URI. |
| Prompts | ¿Qué interacción reutilizable se ofrece? | Entregar una plantilla de instrucciones o mensajes. |

Un servidor puede implementar una o varias de estas categorías; **no es obligatorio que todos los servidores publiquen las tres**.

## 4.4. Capacidades del lado del cliente

Además de consultar capacidades del servidor, MCP contempla mecanismos mediante los cuales un servidor puede requerir información o participación del lado del cliente.

### Roots

Las *roots* permiten que el cliente comunique ubicaciones de trabajo, tradicionalmente directorios o archivos expresados mediante URI. Sirven para proporcionar contexto sobre los espacios relevantes para una operación, pero **no sustituyen los controles de acceso que debe aplicar el servidor o el sistema operativo**.

### Elicitation

La *elicitation* permite solicitar información adicional a la persona usuaria a través del cliente. Puede utilizarse cuando falta un dato o cuando una operación requiere confirmación. El host controla cómo presenta la solicitud y cómo recoge la respuesta.

## 4.5. Transportes de comunicación

El transporte determina cómo circulan los mensajes MCP. Las dos modalidades principales son **stdio** y **Streamable HTTP**. Ambas transportan mensajes del protocolo, basados en **JSON-RPC 2.0**, pero difieren en la forma de conectar los procesos.

### 4.5.1. stdio

En el transporte **standard input / standard output**, el cliente inicia habitualmente el servidor como un proceso hijo y se comunica con él mediante sus flujos de entrada y salida estándar.

- El cliente envía mensajes por la entrada estándar del servidor (*stdin*).
- El servidor responde por su salida estándar (*stdout*).
- Los mensajes de diagnóstico deben mantenerse separados del canal de protocolo, por ejemplo, mediante *stderr*.

Este transporte es especialmente apropiado para servidores locales, aunque que un proceso sea local **no significa** que tenga acceso irrestricto a los archivos: su alcance depende de la configuración y los permisos efectivos.

### 4.5.2. Streamable HTTP

En **Streamable HTTP**, el servidor expone un endpoint HTTP al que el cliente envía solicitudes. Permite implementar servicios independientes y accesibles a través de una red, incluso cuando cliente y servidor se ejecutan en equipos diferentes. El uso de HTTP tampoco implica que el servidor deba ser público: puede operar en una red privada o en la misma máquina.


| Criterio | stdio | Streamable HTTP |
|---|---|---|
| Conexión habitual | Proceso hijo del cliente. | Endpoint HTTP de un servicio independiente. |
| Canal | Entrada y salida estándar. | Solicitudes y respuestas HTTP. |
| Uso frecuente | Integraciones locales. | Servicios locales o remotos. |
| Consideración operativa | Administrar el proceso y separar los logs del protocolo. | Configurar red, autenticación y autorización según el despliegue. |

El transporte histórico **HTTP+SSE** no debe confundirse con Streamable HTTP: fue reemplazado como opción principal y figura como deprecado en la especificación de referencia.

## 4.6. Mensajes, descubrimiento y compatibilidad

MCP utiliza **JSON-RPC 2.0** para expresar solicitudes, respuestas y notificaciones. Métodos como `tools/list`, `resources/read` o `prompts/get` identifican la operación solicitada; los parámetros contienen los datos necesarios para atenderla.

En la versión `2026-07-28`, el núcleo del protocolo es **sin sesiones de protocolo (*stateless*)**: se eliminó el intercambio obligatorio `initialize` / `notifications/initialized` de revisiones anteriores. Las solicitudes incluyen metadatos sobre la versión y las capacidades del cliente. Si necesita consultar las capacidades del servidor previamente, el cliente puede utilizar `server/discover`, pero esa consulta no es obligatoria antes de cada operación.

Esto no significa que toda aplicación deba carecer de estado. Un servicio puede mantener procesos de negocio que requieran continuidad, por ejemplo, mediante identificadores explícitos transmitidos como argumentos. Tampoco significa que todos los clientes y servidores existentes implementen ya la última revisión: la compatibilidad depende de las versiones admitidas por cada implementación.

## 4.7. Conclusión

La arquitectura MCP distingue la aplicación host, el cliente que implementa el protocolo y el servidor que ofrece capacidades externas. Esta separación permite que una aplicación de inteligencia artificial descubra herramientas, consulte recursos y aproveche plantillas de prompt sin confundir la generación de texto con la ejecución efectiva de operaciones.

Los transportes stdio y Streamable HTTP permiten emplear la misma estructura conceptual en distintos entornos de ejecución. Por su parte, las capacidades del cliente, como elicitation y la característica heredada roots, muestran que la interacción puede requerir información adicional y controles de acceso externos al modelo.
