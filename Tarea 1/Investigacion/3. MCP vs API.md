# 3. MCP frente a una API tradicional
## 3.1. Introducción

Una aplicación de inteligencia artificial puede interpretar la solicitud «busca el archivo de configuración y explica qué contiene», pero el modelo de lenguaje, por sí solo, no dispone de una conexión automática con el sistema de archivos. Para realizar esa tarea necesita una aplicación que coordine su interacción con una herramienta capaz de acceder a los archivos autorizados.

Las interfaces de programación de aplicaciones (API) y el Model Context Protocol (MCP) permiten integrar sistemas, pero resuelven problemas de distinto nivel. Una API establece cómo un programa utiliza las funciones de otro. MCP estandariza cómo una aplicación que utiliza modelos de inteligencia artificial descubre y solicita capacidades ofrecidas por servidores compatibles.

## 3.2. ¿Qué es una API?

Una **API** (*Application Programming Interface*, interfaz de programación de aplicaciones) es un contrato entre componentes de software. Define qué operaciones ofrece un sistema, qué datos debe proporcionar quien lo utiliza, cómo se representa la respuesta y qué errores pueden ocurrir. Una API puede ser local o remota; no todas son servicios web.

En una integración tradicional con una API web, la persona desarrolladora consulta la documentación, selecciona el endpoint, construye la petición y programa cómo interpretar la respuesta. La lógica de la aplicación establece qué operación se llama y bajo qué condiciones.

**Ejemplo:** una aplicación necesita consultar información sobre un repositorio:

```javascript
const respuesta = await fetch("https://api.ejemplo.com/repositorios/123");
const repositorio = await respuesta.json();
console.log(repositorio.nombre);
```

La dirección es ficticia. Lo relevante es que la persona que escribió el programa decidió explícitamente la ruta, el momento de la consulta y la manera de utilizar el resultado.

Una API puede incorporar documentación legible por máquinas, como OpenAPI, y puede ser utilizada por agentes de IA si existe una integración que se la presente al modelo. Por tanto, **no sería correcto afirmar que las API carecen de descubrimiento o que solo admiten llamadas fijas**: esa es una característica del ejemplo de integración tradicional, no una limitación universal de las API.

## 3.3. ¿Qué es MCP?

El **Model Context Protocol (MCP)** es un protocolo abierto que estandariza la comunicación entre aplicaciones que utilizan modelos de inteligencia artificial y servidores que ofrecen contexto o capacidades externas. Sus mensajes se basan en **JSON-RPC 2.0**.

Un servidor MCP puede publicar un catálogo de **herramientas** (*tools*). Cada herramienta tiene un nombre, una descripción y un esquema de parámetros de entrada, de manera que el cliente pueda presentarla al modelo como una capacidad disponible. El servidor también puede ofrecer recursos y plantillas de prompt, que se desarrollarán en el documento sobre arquitectura.

En una interacción típica, el proceso es el siguiente:

1. El cliente MCP obtiene la lista de herramientas ofrecidas por el servidor, por ejemplo mediante `tools/list`.
2. La aplicación anfitriona presenta al modelo las herramientas pertinentes, con sus descripciones y parámetros.
3. El modelo propone utilizar una herramienta según la instrucción del usuario y el contexto disponible.
4. La aplicación anfitriona aplica sus políticas y, cuando corresponde, solicita autorización humana.
5. El cliente envía al servidor una solicitud `tools/call` con el nombre de la herramienta y sus argumentos.
6. El servidor ejecuta la operación dentro de sus permisos y devuelve un resultado, que la aplicación puede mostrar al modelo y al usuario.


### Ejemplo simplificado de catálogo de herramientas


```json
{
  "name": "read_file",
  "description": "Lee el contenido de un archivo autorizado",
  "inputSchema": {
    "type": "object",
    "properties": {
      "path": {
        "type": "string",
        "description": "Ruta del archivo que se desea leer"
      }
    },
    "required": ["path"]
  }
}
```

El esquema permite conocer qué argumento necesita la herramienta sin escribir, para cada servidor, una integración específica que describa manualmente todas sus funciones al modelo.

### Ejemplo simplificado de invocación MCP

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "read_file",
    "arguments": {
      "path": "C:\\mcp-practica\\ejemplo.txt"
    }
  }
}
```

La ruta y el nombre de la herramienta son ejemplos. La operación solo podrá realizarse si el servidor ofrece esa herramienta y la ruta se encuentra dentro de su alcance autorizado. Los metadatos y requisitos de transporte adicionales dependen de la versión del protocolo y de la implementación.

## 3.4. Tabla comparativa: API tradicional y MCP

| Criterio | Integración tradicional con una API | Integración mediante MCP |
|---|---|---|
| **Quién decide qué se invoca** | La lógica escrita por la persona desarrolladora selecciona la operación; puede incorporar decisiones dinámicas si así se programa. | El modelo puede proponer una herramienta a partir de la solicitud; el host y el cliente controlan su ejecución y autorización. |
| **Descubrimiento de capacidades** | La persona desarrolladora consulta documentación o descripciones como OpenAPI y programa la integración correspondiente. | El cliente consulta un catálogo estandarizado de herramientas, por ejemplo mediante `tools/list`, con nombres, descripciones y esquemas. |
| **Acoplamiento cliente-servicio** | La integración suele depender de endpoints, parámetros y respuestas concretas de la API. | El cliente puede reutilizar el mismo mecanismo de comunicación con distintos servidores MCP, aunque las herramientas y sus argumentos siguen siendo específicos de cada servidor. |
| **Formato de mensajes** | Depende de la API: puede usar HTTP con JSON, XML, GraphQL, RPC u otros formatos. | MCP utiliza mensajes basados en JSON-RPC 2.0 sobre transportes compatibles, como `stdio` o Streamable HTTP. |
| **Autenticación** | Depende del servicio: claves API, OAuth, sesiones u otros mecanismos. | Depende del transporte y del despliegue; MCP contempla mecanismos de autorización para escenarios HTTP y los servidores locales pueden utilizar permisos del proceso y configuración del entorno. |
| **Consentimiento** | La aplicación debe diseñar cuándo solicita autorización al usuario para acciones sensibles. | El host puede solicitar confirmación antes de invocar herramientas; MCP no garantiza por sí solo que cada operación tenga aprobación humana. |
| **Reutilización entre aplicaciones** | Cada aplicación suele necesitar su propia integración o biblioteca cliente, aunque los estándares y SDK pueden reducir trabajo. | Un servidor MCP puede ser utilizado por diferentes hosts compatibles sin rediseñar su interfaz para cada modelo o aplicación. |
| **Destinatario principal de la descripción de capacidades** | Habitualmente la persona desarrolladora y el software que integra el servicio. | El cliente y, a través de la aplicación anfitriona, el modelo que selecciona herramientas. |
| **Ejemplo en esta actividad** | Programar directamente en Node.js las operaciones para leer y escribir archivos. | Conectar VS Code con un servidor MCP de sistema de archivos que publica operaciones autorizadas. |

**Interpretación:** la diferencia central no es que una API sea «estática» y MCP «inteligente». La diferencia es que MCP proporciona una interfaz común para exponer capacidades a aplicaciones con modelos de IA, mientras que una API define las operaciones de un sistema o servicio particular.

## 3.5. ¿MCP sustituye a las API?

**No. MCP no sustituye a las API ni las vuelve obsoletas.** Son tecnologías complementarias. Un servidor MCP puede envolver una API existente: recibe una llamada estandarizada del cliente MCP, traduce los argumentos a una solicitud dirigida al servicio y devuelve el resultado en un formato que el cliente pueda utilizar.

Por ejemplo:

```text
Usuario
   │ «Consulta las incidencias abiertas»
   ▼
Aplicación con modelo de IA (host)
   │
   ▼
Cliente MCP
   │ tools/call
   ▼
Servidor MCP de incidencias
   │ solicitud a API
   ▼
API del gestor de incidencias
   │ respuesta
   ▼
Servidor MCP → cliente MCP → host → usuario
```

No todos los servidores MCP envuelven una API web. 

## 3.6. Conclusión

Una API establece un contrato para que programas utilicen capacidades de otros componentes. MCP, por su parte, define una forma común de descubrir y utilizar capacidades externas desde aplicaciones que incorporan modelos de inteligencia artificial. Su aporte principal es reducir la necesidad de construir integraciones particulares para presentar cada herramienta al modelo.

La distinción esencial para esta práctica es que el modelo puede proponer una operación, pero el host, el cliente y el servidor participan en su autorización y ejecución. El servidor de sistema de archivos no convierte al modelo en un proceso con acceso directo al disco: proporciona herramientas concretas y sujetas a límites configurados.
